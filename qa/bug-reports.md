## Баг 1 — боевой эндпоинт формы бронирования отвечает 403, заявка не доходит

1. **ID бага:** 1
2. **Среда:** Chromium 151.0.7922.34 (Playwright 1.62.1), Windows 10 Pro 10.0.19045. Дополнительно проверено вне браузера через `Invoke-WebRequest` (Windows PowerShell 5.1).
3. **Предусловия:** открыта `contacts.html` на ширине 1440 px, язык русский, есть выход в интернет (проверено: CORS-запросы к `maxcdn.bootstrapcdn.com` и `cdn.jsdelivr.net` из того же браузера возвращают 200).
4. **Шаги воспроизведения:**
   1. Заполнить все обязательные поля формы корректными данными (ФИО помечено как тестовое).
   2. Нажать «Отправить».
   3. Посмотреть на `#success` и в консоль.
   4. Отдельно запросить эндпоинт из `contacts.html` (`https://script.google.com/macros/s/AKfycb…/exec`) напрямую методом GET.
5. **Ожидаемый результат:** заявка уходит на Google Apps Script, эндпоинт отвечает 2xx, посетитель видит подтверждение.
6. **Фактический результат:** эндпоинт отвечает `403 Forbidden` (`Server: ESF`, тело — HTML-страница Google на 16 863 байта, заголовка `Access-Control-Allow-Origin` нет). Из браузера ответ непрозрачный, `fetch` отклоняется, срабатывает `.catch`, который пишет только в консоль — `#success` остаётся пустым. Заявка не сохраняется, и посетитель не получает никакого сигнала об этом.
7. **Серьёзность:** Blocker — основная бизнес-функция сайта (приём заявок на бронирование) не работает.
8. **Подтверждение:**
   - Ответ на GET к эндпоинту:
     ```
     status: 403 Forbidden
     server: ESF
     ACAO: ''
     content-type: text/html; charset=utf-8
     body length: 16863
     ```
   - Прогон реальной отправки [qa/playwright/real-submit.spec.js](playwright/real-submit.spec.js):
     ```
     Error: expect(locator).toHaveText(expected) failed
     Locator:  locator('#success')
     Expected: "Спасибо, ваша заявка зарегистрирована!"
     Received: ""
     Timeout:  15000ms
     ```

> **Граница достоверности.** 403 воспроизведён с одной машины и одного IP. Возможные причины
> различаются по последствиям: развёртывание веб-приложения отозвано / доступ выставлен не в
> «Anyone» / ограничение со стороны Google по этому запросу. Проверить со стороны владельца:
> открыть URL эндпоинта в браузере, где вы **не** авторизованы в Google, и посмотреть настройку
> «Who has access» у текущего deployment. Само поведение сайта при 403 — баги 2 и 3 — от причины
> не зависит.

## Баг 4 — «Количество заселяющихся» принимает буквы и дробные числа, отрицательное значение превращается в 0

1. **ID бага:** 4
2. **Среда:** Chromium 151.0.7922.34 (Playwright 1.62.1), Windows 10 Pro 10.0.19045.
3. **Предусловия:** открыта `contacts.html`, ширина 1440 px, язык русский, форма пуста.
4. **Шаги воспроизведения:**
   1. В поле «Количество заселяющихся» ввести `-5`, снять фокус (срабатывает `onchange`) — записать значение.
   2. Повторить для `0`, `31`, `abc`, `2.5`.
   3. Проверить, считает ли браузер поле валидным при значении `abc`.
5. **Ожидаемый результат:** нечисловое (`abc`) и дробное (`2.5`) значения не принимаются; `0` не проходит как валидное количество гостей; попытка ввести `-5` даёт ошибку, а не молчаливую замену.
6. **Фактический результат:**

   | Ввод | Значение после `onchange` | Форма валидна |
   |---|---|---|
   | `-5` | `0` | да |
   | `0` | `0` | да |
   | `31` | `30` | да |
   | `abc` | `abc` | да |
   | `2.5` | `2.5` | да |

   То есть в таблицу заявок попадёт `abc`, `2.5` или бронирование на `0` гостей. Зажим границ работает только для чисел, потому что поле объявлено как `type="text"`, а `handleChange()` сравнивает строку с числом (`"abc" < 0` и `"abc" > 30` — оба `false`).
7. **Серьёзность:** Major — мусор в боевой таблице заявок, менеджеру приходится перезванивать и переспрашивать.
8. **Подтверждение:**
   - Скриншот: `qa/screenshots/bug-02-guests-accepts-letters.png`.
   - Красный вывод автотеста `BUG-02`:
     ```
     - Expected  - 3          + Received  + 3
       Object {
         "-5": "0",  "0": "0",  "31": "30",
     -   "2.5": "",            +   "2.5": "2.5",
     -   "abc": "",            +   "abc": "abc",
     -   "abcPassesValidation": false,   +   "abcPassesValidation": true,
       }
     ```
   - Разметка, `contacts.html:71` и `contacts.html:88-91`:
     ```html
     <input type="text" id="text" name="Number_of_clients" required onchange="handleChange(this)">
     ```
     ```js
     function handleChange(input) {
       if (input.value < 0) input.value = 0;
       if (input.value > 30) input.value = 30;
     }
     ```

## Баг 6 — меню залипает раскрытым после сужения окна с 1440 до 375

1. **ID бага:** 6
2. **Среда:** Chromium 151.0.7922.34 (Playwright 1.62.1), Windows 10 Pro 10.0.19045.
3. **Предусловия:** открыта `index.html`, ширина окна 1440 px, меню в обычном горизонтальном виде.
4. **Шаги воспроизведения:**
   1. Кликнуть в любое место страницы (например, по тексту в футере).
   2. Сузить окно до 375 px, ничего больше не нажимая.
   3. Посмотреть на шапку.
5. **Ожидаемый результат:** на 375 px меню свёрнуто под кнопку-гамбургер, как при обычном заходе с телефона.
6. **Фактический результат:** меню остаётся раскрытым вертикальным списком на всю высоту (`min-height: 500px`), одновременно с кнопкой-гамбургером; контент страницы уезжает вниз. Причина: обработчик клика проставляет `.menubar` инлайновый `display: block` в ветке `clientWidth > 1280`, а слушателя `resize` нет — инлайновый стиль перебивает медиазапрос `@media (max-width: 1280px) { .menubar { display: none } }`. Симметричный случай: если открыть гамбургер-меню на 375 px и расширить окно, у `.menubar` остаётся инлайновый `display: flex` вместо `block`.
7. **Серьёзность:** Major — воспроизводится при повороте планшета/телефона и при изменении размера окна на десктопе; страница выглядит сломанной, шапка занимает весь экран.
8. **Подтверждение:**
   - Скриншот: `qa/screenshots/bug-06-menu-stuck-after-resize.png` — на 375 px видны одновременно гамбургер и раскрытый список «Главная / Чайка-1 / Чайка-2 / Чайка-3».
   - Красный вывод автотеста `BUG-06`:
     ```
     Error: после ресайза на 375px меню не свернулось под гамбургер
     expect(received).toMatchObject(expected)
       Object {
     -   "computed": "none",
     +   "computed": "block",
       }
     ```
   - Скрипт, `index.html:43-53` — ветка ширины выполняется только внутри `click`:
     ```js
     document.addEventListener("click", function(e) { … 
       if (document.documentElement.clientWidth > 1280) { m.style.display = 'block'; }
     });
     ```

## Баг 9 — у слайдера на главной цикл стрелок не замкнут

1. **ID бага:** 9
2. **Среда:** Chromium 151.0.7922.34 (Playwright 1.62.1), Windows 10 Pro 10.0.19045.
3. **Предусловия:** открыта `index.html`, ширина 1440 px, слайдер в исходном состоянии (первый слайд, «Чайка-1»).
4. **Шаги воспроизведения:**
   1. Посмотреть, какие стрелки видны на первом слайде.
   2. Переключиться на второй слайд, посмотреть стрелки.
   3. Переключиться на третий (последний) слайд, посмотреть стрелки.
5. **Ожидаемый результат:** на каждом слайде доступны обе стрелки — CSS слайдера написан закольцованным (`#slide16:checked ~ … label:nth-child(1)`, то есть с последнего слайда стрелка «вперёд» ведёт на первый).
6. **Фактический результат:** видимых стрелок по слайдам — `slide1: 1`, `slide2: 2`, `slide3: 1`. На первом слайде нет стрелки «назад», на последнем — «вперёд». Причина: правила в `style.css` рассчитаны на 16 слайдов (как на страницах коттеджей), а на главной их 3, поэтому «замыкающие» селекторы `label:nth-child(16)` и `label:nth-child(4)` не находят элементов. Точки-переключатели при этом работают на все три слайда, вернуться к первому можно ими.

# Баг-репорты — сайт «Коттеджи "Чайка"» (`fmarsm.github.io-main`)

- **Дата прогона:** 2026-08-16
- **Стенд:** `python -m http.server 8080 --directory fmarsm.github.io-main` → `http://localhost:8080`
- **Тест-план:** [test-plan.md](test-plan.md)
- **Автотест:** [playwright/bug-01-date-range.spec.js](playwright/bug-01-date-range.spec.js)

> Ни одна заявка не была отправлена на боевой эндпоинт Google Apps Script.
> Во всех тестах запрос к `script.google.com` перехватывается через `page.route`
> и либо обрывается, либо подменяется локальным ответом.

## BUG-01 — Форма бронирования принимает дату отъезда раньше даты заезда

**1. ID бага:** 1

**2. Среда**
- Браузер: Chromium 151.0.7922.34 (Playwright 1.62.1); воспроизведено также в Chrome 148.0.7778.280
- ОС: Windows 10 Pro, версия 10.0.19045

**3. Предусловия**
- Локальный сервер поднят, открыта страница `http://localhost:8080/contacts.html`
- Ширина окна 1440 px, язык RU
- Форма пуста (страница только что загружена)

**4. Шаги воспроизведения**
1. Заполнить «ФИО» — `TEST QA 2026-08-16`.
2. Заполнить «Номер телефона» — `+79000000000`.
3. В поле «Дата заезда» выбрать `10.09.2026`.
4. В поле «Дата отъезда» выбрать `01.09.2026` (на 9 дней **раньше** заезда).
5. Заполнить «Количество заселяющихся» — `4`.
6. Нажать «Отправить».

**5. Ожидаемый результат**
Форма не отправляется. Пользователю показано сообщение о том, что дата отъезда
не может быть раньше даты заезда. Запрос на сервер не уходит.

**6. Фактический результат**
Валидация отсутствует полностью: `form.checkValidity()` возвращает `true`,
форма отправляется, POST-запрос уходит на боевой эндпоинт с полями
`Date1=2026-09-10`, `Date2=2026-09-01`. Пользователь видит
«Спасибо, ваша заявка зарегистрирована!». Владелец сайта получает в таблицу
заявку с отрицательным сроком проживания.

**7. Серьёзность:** Critical
*Обоснование:* портятся боевые данные бронирования, дефект на основном
бизнес-сценарии сайта, обходного пути на стороне пользователя нет.

**8. Подтверждение**

Автотест `bug-01-date-range.spec.js` падает на текущей версии сайта:

```
  2 failed
    [chromium] › bug-01-date-range.spec.js:28:3 › форма не должна считаться валидной, если отъезд раньше заезда
    [chromium] › bug-01-date-range.spec.js:41:3 › заявка с перевёрнутым интервалом не должна уходить на сервер

    Error: запрос на боевой эндпоинт был отправлен с некорректным интервалом дат:
    Content-Disposition: form-data; name="Date1"
    2026-09-10
    Content-Disposition: form-data; name="Date2"
    2026-09-01
```

Разметка — `contacts.html:67-69`, у полей нет ни `min`/`max`, ни обработчика:

```html
<input type="date" id="text" name="Date1" required autocomplete="off"><br>
<label>Дата отъезда</label><br>
<input type="date" id="text" name="Date2" required autocomplete="off"><br>
```

## BUG-02 — При ошибке сервера показывается «заявка зарегистрирована»; при обрыве сети — не показывается ничего

**1. ID бага:** 2

**2. Среда**
- Браузер: Chromium 151.0.7922.34 (Playwright 1.62.1)
- ОС: Windows 10 Pro, версия 10.0.19045

**3. Предусловия**
- Открыта страница `http://localhost:8080/contacts.html`, ширина 1280 px, язык RU
- Запрос к `https://script.google.com/**` перехвачен и подменён ответом
  `HTTP 500 Internal Server Error` (сценарий А) либо оборван как сетевая
  ошибка (сценарий Б)

**4. Шаги воспроизведения**
1. Заполнить форму корректными данными: ФИО `TEST QA 2026-08-16`,
   телефон `+79000000000`, заезд `01.09.2026`, отъезд `05.09.2026`, гостей `4`.
2. Нажать «Отправить».
3. Посмотреть на текст рядом с кнопкой (`<span id="success">`).

**5. Ожидаемый результат**
- Сценарий А (HTTP 500): пользователю показано сообщение об ошибке, заявка
  не помечена как принятая, данные формы сохранены для повторной отправки.
- Сценарий Б (обрыв сети): пользователю показано сообщение об ошибке.

**6. Фактический результат**
- Сценарий А: показано зелёное «Спасибо, ваша заявка зарегистрирована!»,
  хотя сервер вернул 500 и заявка нигде не сохранена.
- Сценарий Б: не показано **ничего** — сообщение остаётся пустым, ошибка
  уходит только в `console.error`. Пользователь не понимает, отправилась
  заявка или нет.

**7. Серьёзность:** Critical
*Обоснование:* пользователь уверен, что забронировал дом, а заявки нет.
Потеря клиента происходит молча, ни пользователь, ни владелец сайта
об этом не узнают.

**8. Подтверждение**

Скриншот сценария А — под кнопкой «Отправить» зелёное подтверждение
при ответе сервера 500: [screenshots/bug-02-false-success-http-500.png](screenshots/bug-02-false-success-http-500.png)

Скриншот сценария Б — область сообщения пуста: [screenshots/bug-02-network-fail-silent.png](screenshots/bug-02-network-fail-silent.png)

Вывод автотестов:

```
  1) при HTTP 500 пользователь не должен видеть «заявка зарегистрирована»
     Error: сервер ответил 500, а пользователю показано: "Спасибо, ваша заявка зарегистрирована!"
     Expected substring: not "зарегистрирована"
     Received string:        "Спасибо, ваша заявка зарегистрирована!"

  2) при сетевом сбое пользователь должен получить сообщение об ошибке
     Error: при обрыве сети пользователю не показано ничего — заявка «исчезла» молча
     Expected: not ""
```

Причина видна в `contacts.html:97-109` — ответ не проверяется на `response.ok`,
а ветка `.catch` не пишет ничего в интерфейс:

```js
fetch(scriptURL, { method: 'POST', body: new FormData(form)})
  .then(response => {
    success.innerHTML = "Спасибо, ваша заявка зарегистрирована!"
    ...
  })
  .catch(error => console.error('Error!', error.message))
```

## BUG-03 — Ссылка «Контакты» в подвале не работает на всех русских страницах, кроме главной

**1. ID бага:** 3

**2. Среда**
- Браузер: Chromium 151.0.7922.34 (Playwright 1.62.1); воспроизведено также в Chrome 148.0.7778.280
- ОС: Windows 10 Pro, версия 10.0.19045

**3. Предусловия**
- Открыта любая из страниц: `chaika1.html`, `chaika2.html`, `chaika3.html`,
  `contacts.html`; ширина 1440 px, язык RU
- Страница прокручена до подвала

**4. Шаги воспроизведения**
1. Открыть `http://localhost:8080/chaika1.html`.
2. Прокрутить страницу вниз до подвала.
3. Нажать ссылку «Контакты».

**5. Ожидаемый результат**
Переход на страницу `contacts.html` — как это и происходит на `index.html`
и на всех английских страницах.

**6. Фактический результат**
Ничего не происходит: у ссылки `href="#"`, страница остаётся прежней
(добавляется только `#` в адресную строку). Затронуты 4 из 5 русских страниц.
На английских версиях тех же страниц ссылка ведёт на `contacts-eng.html`
корректно — эта асимметрия показывает, что это дефект, а не задумка.

**7. Серьёзность:** Major
*Обоснование:* сломан путь к форме бронирования с карточек коттеджей —
именно оттуда пользователь идёт бронировать. Обходной путь есть
(верхнее меню), поэтому не Critical.

**8. Подтверждение**

Вывод автотестов — 4 страницы из 5 падают, `index.html` проходит:

```
  4 failed
    BUG-03 › chaika1.html: ссылка в подвале ведёт на contacts.html
    BUG-03 › chaika2.html: ссылка в подвале ведёт на contacts.html
    BUG-03 › chaika3.html: ссылка в подвале ведёт на contacts.html
    BUG-03 › contacts.html: ссылка в подвале ведёт на contacts.html

    Error: на chaika1.html ссылка «Контакты» в подвале имеет href="#"
    Expected: "contacts.html"
    Received: "#"
```

Разметка `chaika1.html:211` (аналогично `chaika2.html:218`, `chaika3.html:209`,
`contacts.html:114`):

```html
<div class="footer">
  <a href="#">Контакты</a><br>
```

Для сравнения — `index.html:113` и `chaika1-eng.html:211`:

```html
<a href="contacts.html">Контакты</a><br>     <!-- index.html      -->
<a href="contacts-eng.html">Contacts</a><br> <!-- chaika1-eng.html -->
```

## Приложение. Прочие находки, не оформленные отдельными репортами

Обнаружены по ходу прогона, в тройку по серьёзности не вошли:

| Находка | Где | Предполагаемая серьёзность |
|---|---|---|
| Поле «Количество заселяющихся» принимает нечисловые значения: `abc` и `5abc` проходят валидацию и уходят на сервер без изменений (ограничение 0…30 в `handleChange` срабатывает только на числах) | `contacts.html:71,88-91` | Major |
| На английской главной клик по названию сайта в шапке уводит на **русскую** главную — язык теряется. Единственная из пяти ENG-страниц с таким поведением: остальные четыре ведут на `index-eng.html` | `index-eng.html:20` | Major |
| `<html lang="en">` на всех русских страницах — скринридер читает русский текст английскими правилами, страдает и SEO | все 5 RU-страниц, строка 2 | Major |
| Поле «Номер телефона» (`type="tel"`) без `pattern` принимает любой текст, например `не телефон вообще` | `contacts.html:65` | Minor |
| Дублирующийся `id="text"` — 7 элементов формы на одной странице с одинаковым `id`, невалидный HTML | `contacts.html:63-79` | Minor |
| У формы `action="POST"` вместо `method="POST"`; при отказе JS форма ушла бы GET-запросом на несуществующий файл `POST` | `contacts.html:61` | Minor |
| У всех `<img>` отсутствует атрибут `alt` | все страницы | Minor |

## Что проверено и дефектов не выявлено

- Все 10 страниц отдают HTTP 200, битых ресурсов (4xx/5xx по CSS, шрифтам, изображениям) нет.
- Навигация по верхнему меню на RU и ENG — все 5 пунктов на каждой из 10 страниц
  ведут на существующие страницы своего языка, «протечек» между языками нет.
- Переключение языка кнопками-флагами сохраняет текущую страницу на всех пяти
  парах страниц (проверены все 10 обработчиков `document.location=`).
  Отдельно от этого — ссылка-логотип на `index-eng.html` язык теряет,
  см. приложение выше.
- Бургер-меню на ширинах 375 / 768 / 1024 открывается и закрывается
  (`display: none → flex → none`), на 1440 меню горизонтальное.
- Горизонтальный скролл отсутствует на всех четырёх ширинах для главной,
  карточки коттеджа и контактов — скриншоты в [screenshots/](screenshots/),
  файлы `viewport-<ширина>-<страница>.png`.
